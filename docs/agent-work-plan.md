# Codex 작업 계획

## 목적

이 문서는 `docs/launch-readiness.md`에서 실제 작업을 추출한 Codex용 실행 목록이다. Codex는 사용자에게 별도 판단을 요구하지 않는 `READY` 작업만 수행하고, `WAITING` 작업은 필요한 결정이나 승인이 기록될 때까지 시작하지 않는다.

## 실행 규칙

1. 작업 전 루트 `AGENTS.md`와 관련 문서를 읽는다.
2. Next.js 코드를 수정하기 전 `node_modules/next/dist/docs/`의 관련 가이드를 확인한다.
3. 아래 `READY` 작업을 우선순위와 번호 순서대로 수행한다.
4. 한 작업의 범위를 끝내고 검증한 뒤 상태를 `DONE`으로 변경한다.
5. 요구사항이 불명확하거나 외부 서비스·운영 데이터·비밀값이 필요하면 추측하지 않고 `BLOCKED`로 표시한다.
6. 사용자 원문 없이 인물, 역사, 사상, 연구 내용을 새로 작성하지 않는다.
7. 새로운 의존성, 데이터 모델, 인증 제공자, 배포 서비스는 승인 없이 추가하지 않는다.
8. Production 배포, 운영 DB 변경, 외부 계정 생성, DNS 변경, 실제 메시지 발송은 명시적 승인 없이 수행하지 않는다.
9. 기존 사용자 변경을 보존하고 작업 범위 밖의 파일은 수정하지 않는다.
10. 코드 변경 후 최소한 `npm run lint`와 `npm run build`를 실행한다.

상태 값:

- `READY`: 현재 저장소와 확정된 문서만으로 바로 작업 가능
- `IN_PROGRESS`: 현재 수행 중
- `DONE`: 구현과 검증 완료
- `BLOCKED`: 작업 중 추가 입력 또는 외부 조건이 필요해 중단
- `WAITING`: 사용자 결정 또는 승인이 있어야 시작 가능

## 인증 입력 정책 (OWASP 기준)

- 기준 문서: [OWASP Email Validation and Verification Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html), [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- 이메일:
  - 특정 국내·해외 포털 도메인 목록으로 가입을 제한하지 않고, 명백히 잘못된 형식만 거부해 유효한 기관·학교·자체 도메인을 넓게 허용한다.
  - 도메인 부분은 소문자로 정규화하되 원본 이메일은 표시·발송용으로 보존하고, 가입·로그인·복구에서 동일한 비교 정책을 사용한다.
  - 이메일을 로그인 아이디로 사용하기 전에 소유권을 확인한다. 확인이 끝나지 않은 계정은 관리자 승인 여부와 관계없이 로그인할 수 없다.
  - 이메일 확인과 비밀번호 재설정 토큰은 Supabase Auth에 위임하며, 애플리케이션 DB에 별도 토큰을 저장하거나 전체 확인 URL을 로그에 남기지 않는다.
- 비밀번호:
  - MFA가 없는 현재 서비스에서는 최소 15자, 최대 128자로 허용하고 초과 입력을 자동으로 잘라내지 않는다.
  - 유니코드·공백·특수문자를 포함한 모든 문자를 허용하며 영문자·숫자·특수문자 조합 규칙이나 금지 특수문자 목록을 두지 않는다.
  - 비밀번호 원문과 해시는 애플리케이션 DB에 저장·로그·응답하지 않고 Supabase Auth에 저장과 검증을 위임한다.
  - 회원가입과 비밀번호 변경에서 같은 길이 정책을 적용하고 Supabase Auth의 비밀번호 정책과 일치시킨다.
  - 일반적이거나 유출된 비밀번호 차단과 MFA 적용 여부는 `WAITING-07` 보안 작업에서 검토한다.

### READY-25. 관리자 로그인 방어와 개인정보 조회 범위 축소

- 상태: `DONE`
- 우선순위: 긴급
- 목적: 관리자 credentials 대입 공격을 애플리케이션에서 제한하고, 세션 탈취나 로그인 성공 한 번으로 조회할 수 있는 개인정보 범위를 줄이며, 관리자 비밀번호 변경 즉시 기존 세션을 거부한다.
- 현재 확인 결과:
  - `auth.ts`의 공용 `Credentials.authorize()`에는 IP·계정별 실패 제한과 잠금이 없고 관리자 비밀번호를 일반 문자열 비교로 확인한다. 로그인 Server Action과 `/api/auth/callback/credentials` 직접 요청은 모두 이 경계를 통과한다.
  - 관리자 JWT에는 고정된 `sessionVersion: 0`만 들어가며 `admin-auth.ts`는 현재 환경의 관리자 자격 증명이나 세션 만료를 재검사하지 않는다. Auth.js 기본 세션 만료 외에 관리자 전용 짧은 수명이 없다.
  - 문의 목록은 페이지네이션 없이 모든 행의 이름·이메일·전화·제목·본문을 조회한다. 회원 목록은 필드를 명시적으로 제한하고 있지만 이름·이메일·상태를 모든 행에서 한 번에 조회한다.
  - 연구자 세션은 DB의 `sessionVersion`, 승인·이메일 확인 상태를 요청마다 대조하므로 이번 관리자 JWT 문제와 동일하지 않다.
- 로그인 제한:
  - 두 로그인 진입점이 공유하는 `Credentials.authorize(credentials, request)`의 시작과 종료에 단일 로그인 제한기를 적용한다. Server Action과 callback 라우트에 중복 구현하지 않는다.
  - Prisma에 로그인 제한 레코드를 추가하고 계정과 IP 기준을 각각 검사한다. 계정 식별자와 Vercel의 `x-vercel-forwarded-for`는 `AUTH_SECRET` 기반 HMAC으로 저장해 원문 아이디·이메일·IP를 DB와 로그에 남기지 않는다.
  - 초기 정책은 계정별 15분 내 로그인 시도 5회, IP별 15분 내 로그인 시도 20회를 허용하고 초과 시 15분 잠금으로 한다. 성공 시 해당 계정 시도 상태를 지우고 24시간 지난 제한 레코드를 로그인 처리 중 정리한다.
  - 차단 여부·계정 존재·관리자 여부를 구분하지 않는 동일한 로그인 오류를 반환한다. 제한 저장소 오류 시 관리자 로그인은 우회하지 않고 실패 처리하며 비밀값 없는 원인만 기록한다.
  - 관리자 비밀번호는 Node `crypto.timingSafeEqual()`로 비교하고, 입력 형식 오류·관리자 실패·연구자 실패가 계정 존재 여부를 드러내지 않게 한다. 인위적인 장시간 `sleep`은 서버리스 자원만 점유하므로 추가하지 않는다.
- 관리자 세션 무효화:
  - 로그인 성공 시 `AUTH_SECRET`으로 관리자 아이디·비밀번호를 HMAC한 자격 증명 버전과 1시간 절대 만료 시각을 JWT에 넣는다. 관리자 비밀번호 원문이나 재사용 가능한 해시는 토큰에 넣지 않는다.
  - `requireAdmin()`과 `assertAdmin()`이 역할뿐 아니라 현재 환경에서 다시 계산한 자격 증명 버전과 관리자 만료 시각을 매 요청 검사한다. `ADMIN_PASSWORD` 또는 `ADMIN_USERNAME` 변경 직후 기존 관리자 JWT는 거부한다.
  - 연구자 세션의 기존 DB `sessionVersion` 검사는 유지하고 관리자 전용 필드를 NextAuth 타입에 명시한다.
- 개인정보 조회 범위:
  - 기존 `Pagination`, `parsePageParam()`, `getPostPageWindow()`를 재사용해 관리자 문의·회원 목록을 요청당 10행으로 제한하고 안정적인 정렬을 유지한다.
  - 문의 목록에서는 `message`, `email`, `phone`을 조회하지 않고 접수 유형·상태·제목·이름·접수 시각만 표시한다. 전체 연락처와 본문은 관리자 검사를 거친 `/admin/inquiries/[id]` 상세에서 한 건만 조회한다.
  - 회원 목록은 현재 명시적 `select`를 유지하되 10행 pagination을 적용한다. 비밀번호·Supabase Auth ID·게시글 관계는 계속 조회하지 않는다.
- 검증:
  - 계정·IP 한도 직전과 초과, 잠금 만료, 성공 후 초기화, 제한 저장소 실패 시 관리자 fail-closed를 작은 단위 테스트로 검증한다.
  - 관리자 비밀번호 변경 전 발급 JWT, 1시간 만료 JWT, 역할만 위조한 세션이 `requireAdmin()`과 `assertAdmin()`에서 거부되는지 검증한다.

- Production 적용 제한:
  - 로그인 제한용 migration은 저장소에만 추가하고 운영 DB에는 별도 승인 전 적용하지 않는다.

### WAITING-10. 회원가입 신청·승인 결과 알림 수단 결정

- 상태: `WAITING`
- 우선순위: 높음
- 보류 이유:
  - 이메일 확인과 비밀번호 재설정용 Gmail Custom SMTP는 등록되었으나 관리자 알림 수신자와 승인 결과 문구가 정해지지 않았다.
  - 개인정보가 외부 메시지 서비스로 전달되지 않도록 알림 본문 범위를 먼저 확정해야 한다.
- 확정된 방향:
  - 이메일·비밀번호 인증은 Supabase Auth로 통합한다.
  - 이메일 소유권 확인을 관리자 승인보다 먼저 완료한다.
  - 이메일 확인과 비밀번호 재설정 구현은 관리자 알림과 분리해 `READY-23`에서 진행한다.
  - 이메일 확인과 관리자 승인이 모두 끝나기 전에는 회원 전용 기능에 접근할 수 없다.
  - 애플리케이션의 `User.role`과 `User.status`는 권한과 승인 상태의 기준으로 유지한다.
- 현재 동작:
  - 신청자는 가입 완료 화면에서 관리자 승인 후 로그인할 수 있다는 안내만 받는다.
  - 이메일 소유권을 확인하지 않으며 입력한 이메일 전체를 소문자로 변환해 저장·비교한다.
  - 승인 또는 비활성화 결과를 알려주는 이메일·메시지·상태 조회 기능은 없다.
  - 승인된 경우 로그인이 가능해질 뿐, 신청자에게 승인 사실을 별도로 알리지 않는다.
- 알림 수단 비교:

| 수단 | 초기 비용 | 진입장벽 | 장점 | 주의점 | 적합한 경우 |
| --- | --- | --- | --- | --- | --- |
| Discord Incoming Webhook | webhook용 bot 운영 비용 없음 | 낮음 | 별도 bot 사용자나 인증 흐름 없이 채널 webhook으로 전송 가능 | 담당자가 Discord 서버와 채널을 사용해야 하며 webhook URL을 비밀 값으로 관리해야 함 | 담당자가 이미 Discord를 사용할 때 가장 단순함 |
| Slack Incoming Webhook | Slack workspace 요금제에 따름 | 낮음~중간 | 기존 업무 채널에 바로 쌓이고 담당자 지정이 쉬움 | Slack app 설치 및 workspace·채널 권한이 필요하며 webhook URL을 비밀 값으로 관리해야 함 | 조직이 이미 Slack을 사용할 때 적합함 |
| 이메일(Resend 등) | Resend 무료 구간은 월 3,000건·일 100건 | 중간 | 수신자가 별도 메신저에 가입할 필요가 없고 공식 기록으로 남기 쉬움 | 발신 도메인 확인, API key 및 스팸·전송 실패 관리가 필요함 | 기존 공용 메신저가 없거나 이메일이 공식 연락 수단일 때 적합함 |
| Telegram Bot | Bot API 사용 | 중간 | 소규모 담당자에게 빠르게 알릴 수 있음 | bot token·chat ID 설정이 필요하고 수신자가 Telegram을 사용해야 함 | 담당자가 이미 Telegram을 사용할 때 적합함 |

- 비교 근거: [Discord Webhooks](https://docs.discord.com/developers/resources/webhook), [Slack Incoming Webhooks](https://api.slack.com/messaging/webhooks), [Resend 요금 안내](https://resend.com/pricing?product=marketing), [Telegram Bot API](https://core.telegram.org/bots/api/)

- 권장 결정 순서:
  1. Supabase Auth의 인증 메일과 승인 결과 발송에 사용할 SMTP 제공자를 하나 선택한다.
  2. 같은 SMTP 제공자로 관리자에게 확인 완료된 새 신청을 알리면 메일 전송 기반을 하나로 유지할 수 있다.
  3. Slack·Discord·Telegram은 관리자 즉시 알림이 이메일만으로 부족하다고 확인된 뒤 추가한다.
- 구현 시 최소 범위:
  - 회원가입에서는 특정 이메일 도메인 허용 목록을 사용하지 않고 명백히 잘못된 형식만 거부한다.
  - 가입 이메일·비밀번호와 확인 메일 발송, 확인 토큰 검증은 Supabase Auth에 위임한다.
  - 애플리케이션 `User`에 Supabase Auth 사용자 ID를 연결하고, `auth.users`의 확인 상태와 애플리케이션의 승인 상태를 각각 소유권·권한 기준으로 사용한다.
  - 확인 메일 재발송은 계정 존재 여부를 드러내지 않는 응답과 Supabase Auth의 요청 제한을 사용한다.
  - 이메일 확인과 관리자 승인이 모두 완료된 연구자만 회원 전용 기능에 접근할 수 있게 서버에서 강제한다. Supabase Auth 세션이 있어도 승인되지 않은 계정에는 권한을 부여하지 않는다.
  - 이메일 확인이 끝난 뒤 관리자에게 새 신청 알림을 한 번 전송한다.
  - 관리자 알림에는 이름·이메일을 포함하지 않고 `확인된 새 가입 신청`, 신청 시각, 관리자 회원 관리 화면 링크만 포함한다.
  - 관리자가 계정을 승인하거나 비활성화하면 신청자의 가입 이메일로 결과와 로그인 또는 문의 경로를 전송한다.
  - 알림 실패가 회원가입 성공을 취소하지 않게 하고 서버 로그에 실패 원인을 남긴다.
  - Supabase URL·공개 키와 서버 전용 키, SMTP 비밀값, 발신자 정보는 공개 범위에 맞춰 분리하고 서버 전용 비밀값은 Production 환경 변수로 관리한다.
  - 알림 이력 테이블, 재시도 큐, 여러 채널 동시 발송은 만들지 않는다.
- 필요한 결정:
  1. 관리자 알림 수신 이메일
  2. 승인·비활성화 결과 안내 문구
  3. 신청자에게 표시할 발신자 이름
- 필요한 승인:
  - 관리자 알림과 승인 결과 메일 발송을 Production에서 활성화
- 결정 후 상태 변경:
  - 위 세 항목과 Production 발송이 승인되면 별도 `READY` 작업으로 전환한다.

### WAITING-11. 개인정보처리방침 동의 시점과 재동의 방식 결정

- 상태: `WAITING`
- 우선순위: 높음
- 보류 이유:
  - 현재 회원가입 화면에는 필수 개인정보 동의가 있으나 공개할 개인정보처리방침 전문은 `WAITING-02`의 운영 정보가 확정되어야 완성할 수 있다.
  - 로그인할 때마다 동의를 요구할지, 최초 로그인 또는 방침 변경 때만 요구할지에 따라 UX와 DB 구조가 달라진다.
- 권장안:
  - 개인정보 수집이 시작되는 회원가입 시점에 처리방침 전문을 링크하고 필수 동의를 받는다.
  - 로그인 화면에는 처리방침 링크를 고지하되 매 로그인마다 동의를 요구하지 않는다.
  - 수집·이용 동의를 받은 사항이 변경되었을 때 `동의 버전`과 `동의 시각`을 저장해 재동의를 받는다.
  - 이 항목은 제품 구현 기본안이며 법률 자문을 대신하지 않는다. 최종 문안과 동의 방식은 [개인정보 보호법 제15조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1029334809)를 기준으로 별도 확인한다.
- 대안:
  - 최초 승인 후 첫 로그인 전에 전용 동의 화면을 한 번 표시하고, 동의하지 않으면 계정 페이지와 회원 전용 기능 접근을 막는다.
  - 이 대안을 택하면 사용자 테이블에 동의 버전·동의 시각을 저장하는 migration이 필요하다.
- 필요한 결정:
  1. 가입 시 동의만 받을지, 최초 로그인 동의를 추가할지
  2. 처리방침 변경 시 버전 기반 재동의를 구현할지
  3. `WAITING-02`의 개인정보 보호 담당자 및 연락처, Vercel·Supabase 처리 위치·국외 이전 정보, 공고일·시행일
- 결정 후 상태 변경:
  - 동의 시점과 재동의 정책, 개인정보처리방침 필수 정보가 확정되면 `READY`로 전환한다.

1. **측정부터 추가한다.** `auth.ts`와 `login-throttle.ts`에서 제한 처리(풀/트랜잭션 및 내부 단계), Supabase 인증, 회원 조회·최초 갱신, 성공 후 제한 삭제, 전체 authorize 시간을 나눠 측정한다. 브라우저에서는 제출→pending 표시, 액션 응답, `/auth/continue`, 최종 화면 표시를 분리한다. 임의 요청 ID·구간명·소요 시간만 기록하고 이메일·IP·비밀번호·토큰·쿠키·전체 요청/응답은 남기지 않는다. 테스트 계정·운영 계측 승인을 받은 뒤 관리자/연구자, 성공/실패/차단, 첫 요청/재요청을 비교한다. 소수 표본은 중앙값·최댓값·표본 수로 보고하고 충분한 표본 없이 p95를 확정하지 않는다.
2. **DB 왕복이 지배적이면 제한 처리부터 줄인다.** 매 로그인에서 수행하는 전체 만료 레코드 정리를 인증 필수 경로 밖으로 옮길 수 있는 기존 유지보수 수단을 확인하고, 24시간 보존 정책을 지킬 방법이 정해진 뒤 변경한다. 키별 초기화·확인·증가를 원자적인 조건부 upsert 등으로 합치는 최소 변경을 검토한다. 적용 전 동시 요청과 잠금 경계를 테스트한다. 단순 `Promise.all`이나 프로세스 메모리 제한기로 교체하지 않는다. 계정 5회/IP 20회, 15분 창·차단, 관리자 fail-closed 및 기존 오류 정책을 임의로 완화하지 않는다. 성공 후 제한 삭제도 측정 없이 fire-and-forget으로 옮기지 않는다.
3. **외부 호출이 지배적이면 연결 환경을 확인한다.** 실제 Vercel 함수 실행 지역과 Supabase Auth·DB 지역, 커넥션 풀 대기, 첫 요청 초기화 비용을 확인한다. 지역/풀 설정 변경은 근거와 별도 운영 승인 후 적용한다. 비밀번호 검증을 생략하거나 Supabase와 병렬로 무조건 회원 정보를 조회하지 않는다. SDK 교체·Redis·새 인증 제공자 도입은 범위 밖이다.
4. **후속 이동이 지배적일 때만 단축한다.** 검증된 서버 세션 역할에 따라 안전하게 직접 목적지를 정할 수 있는지 설치된 Auth.js 동작을 확인한다. 클라이언트 username만으로 관리자 목적지나 권한을 판단하지 않는다. 중간 경로 제거가 복잡하거나 절감이 작으면 유지한다. 홈 캐시 미스가 원인이면 무거운 자료 영역만 Suspense로 분리하는 방안을 검토하고, 인증 화면 전체 재구성은 하지 않는다.
5. **동일 조건으로 전후 검증한다.** 단계별 시간·실제 SQL 왕복 수와 클릭→최종 화면 시간을 비교해 효과를 기록한다. 승인/미승인/비활성/이메일 미확인/세션 무효화 검사를 보존한다. 운영 지연이 확인되지 않은 단계는 변경하지 않는다.
