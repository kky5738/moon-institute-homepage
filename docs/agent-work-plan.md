# Codex 작업 계획

## 목적

이 문서는 `docs/launch-readiness.md`에서 실제 작업을 추출한 Codex용 실행 목록이다. Codex는 사용자에게 별도 판단을 요구하지 않는 `READY` 작업만 수행하고, `WAITING` 작업은 필요한 결정이나 승인이 기록될 때까지 시작하지 않는다.

## 실행 규칙

1. 작업 전 루트 `AGENTS.md`와 관련 문서를 읽는다.
2. Next.js 코드를 수정하기 전 `node_modules/next/dist/docs/`의 관련 가이드를 확인한다.
3. 아래 `READY` 작업을 우선순위와 번호 순서대로 수행한다.
4. 한 작업의 범위를 끝내고 검증한 뒤 상태를 `DONE`으로 변경한다.
5. 요구사항이 불명확하거나 외부 서비스·운영 데이터·비밀값이 필요하면 추측하지 않고 `BLOCKED`로 표시한다.
6. 사용자 원문 없이 인물, 역사, 사상, 연구 내용을 새로 작성하지 않는다.
7. 새로운 의존성, 데이터 모델, 인증 제공자, 배포 서비스는 승인 없이 추가하지 않는다.
8. Production 배포, 운영 DB 변경, 외부 계정 생성, DNS 변경, 실제 메시지 발송은 명시적 승인 없이 수행하지 않는다.
9. 기존 사용자 변경을 보존하고 작업 범위 밖의 파일은 수정하지 않는다.
10. 코드 변경 후 최소한 `npm run lint`와 `npm run build`를 실행한다.

상태 값:

- `READY`: 현재 저장소와 확정된 문서만으로 바로 작업 가능
- `IN_PROGRESS`: 현재 수행 중
- `DONE`: 구현과 검증 완료
- `BLOCKED`: 작업 중 추가 입력 또는 외부 조건이 필요해 중단
- `WAITING`: 사용자 결정 또는 승인이 있어야 시작 가능

## 인증 입력 정책 (OWASP 기준)

- 기준 문서: [OWASP Email Validation and Verification Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html), [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- 이메일:
  - 특정 국내·해외 포털 도메인 목록으로 가입을 제한하지 않고, 명백히 잘못된 형식만 거부해 유효한 기관·학교·자체 도메인을 넓게 허용한다.
  - 도메인 부분은 소문자로 정규화하되 원본 이메일은 표시·발송용으로 보존하고, 가입·로그인·복구에서 동일한 비교 정책을 사용한다.
  - 이메일을 로그인 아이디로 사용하기 전에 소유권을 확인한다. 확인이 끝나지 않은 계정은 관리자 승인 여부와 관계없이 로그인할 수 없다.
  - 이메일 확인과 비밀번호 재설정 토큰은 Supabase Auth에 위임하며, 애플리케이션 DB에 별도 토큰을 저장하거나 전체 확인 URL을 로그에 남기지 않는다.
- 비밀번호:
  - MFA가 없는 현재 서비스에서는 최소 15자, 최대 128자로 허용하고 초과 입력을 자동으로 잘라내지 않는다.
  - 유니코드·공백·특수문자를 포함한 모든 문자를 허용하며 영문자·숫자·특수문자 조합 규칙이나 금지 특수문자 목록을 두지 않는다.
  - 비밀번호 원문과 해시는 애플리케이션 DB에 저장·로그·응답하지 않고 Supabase Auth에 저장과 검증을 위임한다.
  - 회원가입과 비밀번호 변경에서 같은 길이 정책을 적용하고 Supabase Auth의 비밀번호 정책과 일치시킨다.
  - 일반적이거나 유출된 비밀번호 차단과 MFA 적용 여부는 `WAITING-07` 보안 작업에서 검토한다.

## 바로 작업 가능한 일

### READY-01. 문서 정합성 점검

- 상태: `DONE`
- 우선순위: 높음
- 목적: 현재 코드와 운영 문서가 서로 다른 내용을 안내하지 않게 한다.
- 작업:
  - `README.md`, `docs/sitemap.md`, `docs/deployment-checklist.md`, `docs/launch-readiness.md`를 실제 라우트, 스크립트, 인증 방식과 대조한다.
  - 명백히 오래되거나 잘못된 설명만 현재 구현에 맞게 수정한다.
  - Vercel·Supabase의 확정된 구성과 아직 확인하지 않은 설정을 구분하고, 공식 콘텐츠와 회원 정책은 확정된 것처럼 쓰지 않는다.
- 완료 조건:
  - 현재 실행 방법, 공개·관리자 경로, 단일 관리자 인증 방식이 코드와 일치한다.
  - 미결정 사항은 미결정 상태로 남는다.

### READY-02. 랜딩 페이지의 두 탐색 기능 차별화

- 상태: `DONE`
- 우선순위: 높음
- 목적: 연구 주제 허브와 자료 해설형 아카이브가 서로 다른 역할로 인식되게 한다.
- 기준 문서: `docs/proposal.md`, `docs/launch-readiness.md`
- 작업:
  - 기존 홈 컴포넌트와 데이터 흐름을 먼저 확인한다.
  - 연구 주제 허브는 생애·말씀·업적을 보여주는 주요 탐색 영역으로 유지한다.
  - 자료 아카이브는 같은 형태의 주제 카드 반복이 아니라 `처음 읽을 자료` 중심의 조밀한 목록 또는 읽기 경로로 표현한다.
  - 기존 데이터만 사용하고 공식 연구 내용을 임의로 만들지 않는다.
  - 새로운 UI·모션 의존성을 추가하지 않는다.
  - 모바일과 데스크톱에서 정보 위계와 내부 링크를 확인한다.
- 완료 조건:
  - 두 섹션의 제목을 가려도 레이아웃과 정보 구조에서 역할 차이가 보인다.
  - 홈에서 `주제 → 대표 자료 → 다음 자료` 흐름으로 이동할 수 있다.
  - 빈 자료 상태에서도 잘못된 추천이나 존재하지 않는 링크를 노출하지 않는다.
  - `npm run lint`와 `npm run build`가 통과한다.

### READY-03. 주제·자료 연결 무결성 점검

- 상태: `DONE`
- 우선순위: 높음
- 목적: 현재 slug 기반 수동 연결이 조용히 끊어진 상태를 찾고 수정한다.
- 작업:
  - `src/lib/topics.ts`, `src/lib/material-guides.ts`, `prisma/seed.ts`의 주제 slug, 카테고리 slug, 추천 자료 slug를 대조한다.
  - 공개 라우트와 내부 링크의 대상이 실제로 존재하는지 확인한다.
  - 불일치는 기존 구조 안에서 가장 작은 수정으로 해결한다.
  - 공식 콘텐츠를 새로 작성하거나 새 데이터 모델을 만들지 않는다.
- 완료 조건:
  - 생애·말씀·업적 주제의 카테고리 연결이 seed 데이터와 일치한다.
  - 추천 자료가 없을 때 기존 fallback이 정상 작동한다.
  - 확인한 연결 관계와 예외를 관련 운영 문서에 짧게 남긴다.
  - `npm run lint`와 `npm run build`가 통과한다.

### READY-04. 접근성 및 기본 인터페이스 점검

- 상태: `DONE`
- 우선순위: 중간
- 목적: 공식 개시에 필요한 기본 접근성과 조작 피드백을 확보한다.
- 적용 지침: `.agents/skills/apple-design/SKILL.md`
- 작업:
  - 공개 페이지와 관리자 폼의 제목 구조, landmark, label, 키보드 포커스, 링크·버튼 구분을 점검한다.
  - 모바일 터치 영역, 텍스트 대비, 오류·성공 상태 전달을 점검한다.
  - 기존 애니메이션이 있다면 `prefers-reduced-motion` 대응을 확인한다.
  - 명백한 접근성 결함은 기존 CSS와 HTML로 수정한다.
  - Apple 스타일을 이유로 장식 효과나 모션 라이브러리를 추가하지 않는다.
- 완료 조건:
  - 키보드만으로 주요 공개 탐색과 관리자 폼을 사용할 수 있다.
  - 입력 오류와 성공 상태가 색상만으로 전달되지 않는다.
  - 움직임이 필수 정보를 가리거나 reduced-motion 설정을 무시하지 않는다.
  - `npm run lint`와 `npm run build`가 통과한다.

### READY-05. 현재 관리자 운영 안내서 작성

- 상태: `DONE`
- 우선순위: 중간
- 목적: 단일 관리자가 현재 구현된 기능을 안전하게 운영할 수 있게 한다.
- 산출물: `docs/admin-operations.md`
- 작업:
  - 로그인, 게시글 초안·공개·보관, slug 관리, 문의 상태 변경 흐름을 실제 화면과 코드 기준으로 설명한다.
  - 게시글 및 카테고리 slug 변경 시 주제·추천 연결 확인 사항을 포함한다.
  - 환경 변수의 실제 값이나 운영 비밀은 기록하지 않는다.
  - 아직 없는 회원 승인, 파일 업로드, 복원 기능을 있는 것처럼 설명하지 않는다.
- 완료 조건:
  - 새 운영자가 현재 관리자 화면의 지원 범위와 제한을 이해할 수 있다.
  - 데이터 삭제 대신 보관 상태를 사용하는 현재 정책이 명시되어 있다.

### READY-06. 로컬 공식 개시 QA

- 상태: `DONE`
- 우선순위: 중간
- 목적: 배포 전 현재 저장소에서 확인 가능한 공개·관리자 흐름을 검증한다.
- 작업:
  - `npm run lint`와 `npm run build`를 실행한다.
  - 홈, 주제 목록·상세, 자료 목록·상세, 공지 목록·상세, 문의, 로그인, 관리자 경로를 데스크톱과 모바일 크기로 확인한다.
  - 인증이 필요한 변경 작업은 로컬 개발 DB에서만 수행하고, 기존 데이터가 중요하거나 환경이 불명확하면 읽기 검증까지만 한다.
  - 발견한 재현 가능한 결함은 현재 범위 안에서 수정하고 다시 검증한다.
  - 결과와 남은 외부 환경 검증 항목을 `docs/launch-readiness.md`에 날짜와 함께 기록한다.
- 완료 조건:
  - 주요 경로에서 깨진 화면, 잘못된 링크, 처리되지 않은 런타임 오류가 없다.
  - 로컬에서 확인할 수 없는 Production 항목은 완료 처리하지 않는다.

### READY-07. 회원가입과 일반 로그인

- 상태: `DONE`
- 우선순위: 높음
- 목적: 연구원이 이메일과 비밀번호로 가입하고, 관리자 승인 후 로그인할 수 있게 한다.
- 개인정보 기준: `docs/privacy-policy.md`
- 승인된 최소 범위:
  - 공개 회원가입 계정은 `RESEARCHER`, `PENDING` 상태로 생성한다.
  - 관리자가 계정을 승인하거나 비활성화할 수 있다.

### READY-18. 연구 게시판 전통형 UI와 Supabase Storage 파일 업로드

- 상태: `BLOCKED`
- 우선순위: 높음
- 목적: 연구 게시판을 데스크톱에서는 조밀한 전통형 목록과 문서형 상세 화면으로 제공하고, 현재 인증을 유지한 채 연구 글에 문서 첨부와 본문 이미지를 안전하게 추가한다.
- 승인된 최소 범위:
  - `/research` 목록을 `번호 | 제목 | 첨부 | 작성자 | 작성일` 중심의 한 줄 행으로 정리하고 요약문을 목록에서 제거한다.
  - `/research/[slug]`는 넓은 게시판 프레임 안에 읽기 폭이 제한된 본문을 두고 제목·메타데이터·첨부 영역을 모바일과 데스크톱에 맞게 재배치한다.
  - 첨부 문서는 PDF, HWP, DOCX만 허용하고 파일당 크기를 20MiB로 제한한다.
  - 본문 이미지는 JPEG, PNG, WebP를 허용하고 같은 20MiB 제한을 적용한다.
  - 드래그앤드롭, 이미지 미리보기, 다중 업로드 진행률, 범용 리치 텍스트·Markdown 편집기는 추가하지 않는다.
- Supabase Auth 독립 구조:
  - 현재 `assertResearcher()`와 게시글 작성자 검사를 업로드 권한의 기준으로 유지하고, 클라이언트가 Supabase `auth.uid()` 또는 service key에 직접 의존하지 않게 한다.
  - 서버 전용 Supabase 클라이언트가 private bucket의 signed upload URL을 발급하고 브라우저는 그 URL로 Storage에 직접 전송한다.
  - service/secret key는 서버 환경 변수에서만 읽고 클라이언트 번들, 응답, DB와 로그에 포함하지 않는다.
  - 저장 경로는 애플리케이션 `User.id`, `Post.id`와 무작위 UUID를 사용해 구성하고 원본 파일명이나 향후 Supabase Auth 사용자 ID에 의존하지 않는다.
  - Supabase Auth 도입 시 Storage·첨부 모델·본문 표식은 유지하고, 업로드와 수정 경계의 현재 인증 검사만 Supabase 세션 기반 검사로 교체한다.
- 데이터 모델과 저장 흐름:
  - `PostAttachment`에 UUID, 게시글 관계, 용도(`ATTACHMENT` 또는 `INLINE_IMAGE`), 원본명, Storage object path, MIME, 크기, 이미지 대체 텍스트, 생성·삭제 시각을 저장한다.

  - 게시글 보관은 첨부 object를 물리 삭제하지 않고 장기 보존하며, 작성자가 첨부를 제거할 때도 관계를 soft delete해 운영 복구 여지를 남긴다.
  - 공개 글은 게시글 상태를 서버에서 확인한 뒤 짧은 만료시간의 다운로드·이미지 URL을 생성하고, 초안은 작성자 또는 관리자에게만 제공한다.

  - 이메일 소유권을 확인하지 않으며 입력한 이메일 전체를 소문자로 변환해 저장·비교한다.
  - 승인 또는 비활성화 결과를 알려주는 이메일·메시지·상태 조회 기능은 없다.
  - 승인된 경우 로그인이 가능해질 뿐, 신청자에게 승인 사실을 별도로 알리지 않는다.
- 알림 수단 비교:

| 수단 | 초기 비용 | 진입장벽 | 장점 | 주의점 | 적합한 경우 |
| --- | --- | --- | --- | --- | --- |

- 권장 결정 순서:
  1. Supabase Auth의 인증 메일과 승인 결과 발송에 사용할 SMTP 제공자를 하나 선택한다.
  2. 같은 SMTP 제공자로 관리자에게 확인 완료된 새 신청을 알리면 메일 전송 기반을 하나로 유지할 수 있다.
  3. Slack·Discord·Telegram은 관리자 즉시 알림이 이메일만으로 부족하다고 확인된 뒤 추가한다.
- 구현 시 최소 범위:
  - 회원가입에서는 특정 이메일 도메인 허용 목록을 사용하지 않고 명백히 잘못된 형식만 거부한다.
  - 가입 이메일·비밀번호와 확인 메일 발송, 확인 토큰 검증은 Supabase Auth에 위임한다.
  - 애플리케이션 `User`에 Supabase Auth 사용자 ID를 연결하고, `auth.users`의 확인 상태와 애플리케이션의 승인 상태를 각각 소유권·권한 기준으로 사용한다.
  - 확인 메일 재발송은 계정 존재 여부를 드러내지 않는 응답과 Supabase Auth의 요청 제한을 사용한다.
  - 이메일 확인과 관리자 승인이 모두 완료된 연구자만 회원 전용 기능에 접근할 수 있게 서버에서 강제한다. Supabase Auth 세션이 있어도 승인되지 않은 계정에는 권한을 부여하지 않는다.
  - 이메일 확인이 끝난 뒤 관리자에게 새 신청 알림을 한 번 전송한다.
  - 관리자 알림에는 이름·이메일을 포함하지 않고 `확인된 새 가입 신청`, 신청 시각, 관리자 회원 관리 화면 링크만 포함한다.
  - 관리자가 계정을 승인하거나 비활성화하면 신청자의 가입 이메일로 결과와 로그인 또는 문의 경로를 전송한다.
  - 알림 실패가 회원가입 성공을 취소하지 않게 하고 서버 로그에 실패 원인을 남긴다.
  - Supabase URL·공개 키와 서버 전용 키, SMTP 비밀값, 발신자 정보는 공개 범위에 맞춰 분리하고 서버 전용 비밀값은 Production 환경 변수로 관리한다.
  - 알림 이력 테이블, 재시도 큐, 여러 채널 동시 발송은 만들지 않는다.
- 필요한 결정:
  1. Supabase Auth와 승인 결과 알림에 사용할 SMTP 제공자
  2. 이메일 확인 링크의 유효시간
  3. 관리자 알림 수신 이메일과 신청자에게 표시할 발신자
  4. 확인·승인·비활성화 결과 안내 문구
  5. 서비스 계정 생성 및 비밀 키 등록 담당자
- 필요한 승인:
  - `User`와 Supabase Auth 사용자 ID 연결 및 기존 자체 비밀번호 해시 제거를 위한 Prisma 모델과 migration
  - Supabase Auth 활성화, 이메일 확인 설정, redirect URL 허용 목록, SMTP와 Production 비밀값 등록
- 결정 후 상태 변경:
  - 위 다섯 항목이 정해지고 데이터 모델 변경과 Supabase Auth Production 설정이 승인되면 `READY`로 전환한다.

### WAITING-11. 개인정보처리방침 동의 시점과 재동의 방식 결정

- 상태: `WAITING`
- 우선순위: 높음
- 보류 이유:
  - 현재 회원가입 화면에는 필수 개인정보 동의가 있으나 공개할 개인정보처리방침 전문은 `WAITING-02`의 운영 정보가 확정되어야 완성할 수 있다.
  - 로그인할 때마다 동의를 요구할지, 최초 로그인 또는 방침 변경 때만 요구할지에 따라 UX와 DB 구조가 달라진다.
- 권장안:
  - 개인정보 수집이 시작되는 회원가입 시점에 처리방침 전문을 링크하고 필수 동의를 받는다.
  - 로그인 화면에는 처리방침 링크를 고지하되 매 로그인마다 동의를 요구하지 않는다.
  - 수집·이용 동의를 받은 사항이 변경되었을 때 `동의 버전`과 `동의 시각`을 저장해 재동의를 받는다.
  - 이 항목은 제품 구현 기본안이며 법률 자문을 대신하지 않는다. 최종 문안과 동의 방식은 [개인정보 보호법 제15조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1029334809)를 기준으로 별도 확인한다.
- 대안:
  - 최초 승인 후 첫 로그인 전에 전용 동의 화면을 한 번 표시하고, 동의하지 않으면 계정 페이지와 회원 전용 기능 접근을 막는다.
  - 이 대안을 택하면 사용자 테이블에 동의 버전·동의 시각을 저장하는 migration이 필요하다.
- 필요한 결정:
  1. 가입 시 동의만 받을지, 최초 로그인 동의를 추가할지
  2. 처리방침 변경 시 버전 기반 재동의를 구현할지
  3. `WAITING-02`의 개인정보 보호 담당자 및 연락처, Vercel·Supabase 처리 위치·국외 이전 정보, 공고일·시행일
- 결정 후 상태 변경:
  - 동의 시점과 재동의 정책, 개인정보처리방침 필수 정보가 확정되면 `READY`로 전환한다.

### WAITING-12. Supabase Auth 비밀번호 재설정 통합

- 상태: `WAITING`
- 우선순위: 높음
- 확정된 방향:
  - 현재 자체 이메일·비밀번호 인증을 Supabase Auth로 교체한다.
  - 이메일 확인과 비밀번호 재설정은 Supabase Auth의 동일한 인증 사용자와 메일 설정을 사용한다.
  - 애플리케이션의 `User.passwordHash`는 인증 기준으로 사용하지 않으며 전환 완료 후 제거한다.
  - 초기 운영의 SMTP 제공자와 추후 공식 도메인 발신 계정은 Supabase Auth의 SMTP 설정으로 교체할 수 있게 한다.
  - 별도 재설정 토큰 모델, 자체 토큰 발급 코드, 이메일 발송 API와 작업 큐는 만들지 않는다.
- 구현 계획:
  1. 로그인 화면에 `비밀번호를 잊으셨나요?` 링크와 이메일 입력 화면을 추가한다.
  2. 존재하는 계정인지와 관계없이 같은 완료 문구를 반환해 회원 이메일 존재 여부가 노출되지 않게 한다.
  3. 서버에서 Supabase Auth의 비밀번호 재설정 메일 API를 호출하고 계정별·IP별 요청 제한을 적용한다.
  4. 재설정 링크의 redirect URL은 명시적인 Production URL 허용 목록 안에서만 생성하고 토큰이나 전체 링크를 로그에 남기지 않는다.
  5. callback에서 Supabase Auth 세션을 검증하고 기존 비밀번호 정책으로 새 비밀번호를 검사한 뒤 Supabase Auth의 사용자 비밀번호를 변경한다.
  6. 성공 후 다른 기존 세션을 무효화하고 재사용·만료·변조된 링크는 거부한다.
  7. 발송 실패는 사용자에게 계정 존재 여부나 내부 오류를 노출하지 않고 서버에 비밀값을 제외한 오류만 기록한다.
- 설정 및 비밀값 관리:
  - Site URL과 redirect URL 허용 목록은 Production 공식 주소만 정확히 등록하고 Preview·개발 주소는 필요한 범위에 한해 분리한다.
  - SMTP 호스트·계정·비밀번호와 발신자 정보는 Supabase Auth의 Production SMTP 설정에서 관리한다.
  - 서버 전용 Supabase 비밀값은 Vercel Production 환경 변수에만 등록하고 클라이언트 번들 또는 Preview 환경에 노출하지 않는다.
  - 로컬과 Preview 발송 시험이 필요할 때는 운영 계정과 분리된 테스트 프로젝트 또는 테스트 계정을 사용한다.
- 공식 도메인 구매 후 변경:
  - 웹 도메인은 Vercel에 연결하고 Supabase Auth의 Site URL과 redirect URL 허용 목록을 공식 주소로 변경한다.
  - 웹 도메인을 연결하는 것만으로 해당 도메인의 이메일 발신 권한이 생기지는 않는다.
  - 공식 주소로 메일을 보내려면 별도 메일 계정 또는 발송 서비스를 준비하고 제공자가 요구하는 SPF·DKIM DNS 레코드를 등록한다.
  - 확인이 끝나면 Supabase Auth의 SMTP와 발신자 설정을 공식 계정 값으로 교체한다.
- 기본 보안값:
  - 초기화 링크 유효시간: 30분
  - 토큰 발급·검증·저장: Supabase Auth에 위임
  - 재발송 대기시간: 계정별 최소 60초와 Supabase Auth rate limit 적용
  - 응답: 계정 존재 여부와 발송 성공 여부를 구분하지 않는 공통 문구
- 필요한 입력 및 승인:
  1. 사용할 SMTP 제공자와 Supabase Auth에서의 사용 가능 여부
  2. Supabase Auth의 Site URL, redirect URL, 이메일 템플릿, SMTP 설정 담당자
  3. `User`와 Supabase Auth 사용자 연결 및 기존 사용자 전환 migration의 Production DB 적용 승인
  4. 기존 사용자는 비밀번호 해시를 이전하지 않고 초대 또는 재설정 메일로 새 비밀번호를 설정한다는 운영 승인
  5. Supabase Auth의 기존 세션 무효화 방식과 관리자 계정 전환 범위 확정
- 완료 조건:
  - 등록 이메일과 미등록 이메일 요청이 화면과 응답 시간에서 계정 존재 여부를 드러내지 않는다.
  - 유효한 링크로 한 번만 비밀번호를 변경할 수 있고 만료·재사용·변조 토큰은 거부된다.
  - 새 비밀번호로 로그인할 수 있고 이전 비밀번호와 무효화 대상 기존 세션은 사용할 수 없다.
  - 실제 SMTP 비밀번호·서버 전용 Supabase 비밀값·원문 토큰이 저장소, 애플리케이션 DB, 로그에 남지 않는다.
  - 이메일 미확인 계정은 관리자 승인과 회원 전용 기능 접근 대상이 되지 않는다.
  - 관련 인증 테스트, `npm run lint`, `npm run build`가 통과한다.
- 결정 후 상태 변경:
  - SMTP 제공자, Supabase Auth Production 설정, 기존 사용자 전환 범위와 DB migration 승인이 확정되면 `READY`로 전환한다.

### WAITING-13. Production 성능 운영 측정

- 상태: `WAITING`
- 우선순위: 중간
- 목적: 코드 추측이 아니라 Production 지표로 다음 병목과 인프라 변경 필요성을 판단한다.
- 현재 기준선:
  - Next.js 16.2.6 production build는 성공하며 빌드 자체는 정상 범위다.
  - 2026-08-26 기준 App Router 25개 경로가 모두 동적 렌더링된다.
  - 로컬 `DATABASE_URL`은 Supabase Tokyo(`ap-northeast-1`) transaction pooler를 사용한다.
  - Vercel Function 지역, p50/p95 TTFB·실행시간·호출량과 Supabase query latency·pool wait는 저장소만으로 확인할 수 없다.
- 필요한 입력 및 승인:
  1. Vercel Production 프로젝트의 Function region과 Observability 지표 조회 권한 또는 내보낸 측정값
  2. Supabase Production의 query latency와 pool wait 지표 조회 권한 또는 내보낸 측정값
  3. Production에 영향을 주지 않는 smoke 측정 경로와 시간대
- 측정 및 판단:
  - 대표 공개 경로의 p50/p95 TTFB, Function duration과 invocation을 개선 전후 같은 조건에서 비교한다.
  - Vercel Function과 Supabase의 지역이 다르면 데이터 소스에 가까운 Function 배치를 우선 검토한다.
  - 실제 느린 쿼리는 `EXPLAIN ANALYZE`로 확인한 뒤에만 복합 인덱스를 제안한다.
  - Next.js 내장 캐시 적용 후에도 공유 캐시, 분산 rate limit 또는 queue 필요성이 측정될 때만 Redis를 검토한다.
- 완료 조건:
  - 대표 경로별 기준선과 개선 후 p50/p95가 날짜·환경과 함께 기록된다.
  - Function 지역과 Supabase 지역의 일치 여부가 확인된다.
  - 인덱스·region·Redis 변경 여부가 측정 근거와 함께 결정된다.
