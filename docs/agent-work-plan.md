# Codex 작업 계획

## 목적

이 문서는 `docs/launch-readiness.md`에서 실제 작업을 추출한 Codex용 실행 목록이다. Codex는 사용자에게 별도 판단을 요구하지 않는 `READY` 작업만 수행하고, `WAITING` 작업은 필요한 결정이나 승인이 기록될 때까지 시작하지 않는다.

## 실행 규칙

1. 작업 전 루트 `AGENTS.md`와 관련 문서를 읽는다.
2. Next.js 코드를 수정하기 전 `node_modules/next/dist/docs/`의 관련 가이드를 확인한다.
3. 아래 `READY` 작업을 우선순위와 번호 순서대로 수행한다.
4. 한 작업의 범위를 끝내고 검증한 뒤 상태를 `DONE`으로 변경한다.
5. 요구사항이 불명확하거나 외부 서비스·운영 데이터·비밀값이 필요하면 추측하지 않고 `BLOCKED`로 표시한다.
6. 사용자 원문 없이 인물, 역사, 사상, 연구 내용을 새로 작성하지 않는다.
7. 새로운 의존성, 데이터 모델, 인증 제공자, 배포 서비스는 승인 없이 추가하지 않는다.
8. Production 배포, 운영 DB 변경, 외부 계정 생성, DNS 변경, 실제 메시지 발송은 명시적 승인 없이 수행하지 않는다.
9. 기존 사용자 변경을 보존하고 작업 범위 밖의 파일은 수정하지 않는다.
10. 코드 변경 후 최소한 `npm run lint`와 `npm run build`를 실행한다.

상태 값:

- `READY`: 현재 저장소와 확정된 문서만으로 바로 작업 가능
- `IN_PROGRESS`: 현재 수행 중
- `DONE`: 구현과 검증 완료
- `BLOCKED`: 작업 중 추가 입력 또는 외부 조건이 필요해 중단
- `WAITING`: 사용자 결정 또는 승인이 있어야 시작 가능

## 바로 작업 가능한 일

### READY-01. 문서 정합성 점검

- 상태: `DONE`
- 우선순위: 높음
- 목적: 현재 코드와 운영 문서가 서로 다른 내용을 안내하지 않게 한다.
- 작업:
  - `README.md`, `docs/sitemap.md`, `docs/deployment-checklist.md`, `docs/launch-readiness.md`를 실제 라우트, 스크립트, 인증 방식과 대조한다.
  - 명백히 오래되거나 잘못된 설명만 현재 구현에 맞게 수정한다.
  - Vercel·Supabase의 확정된 구성과 아직 확인하지 않은 설정을 구분하고, 공식 콘텐츠와 회원 정책은 확정된 것처럼 쓰지 않는다.
- 완료 조건:
  - 현재 실행 방법, 공개·관리자 경로, 단일 관리자 인증 방식이 코드와 일치한다.
  - 미결정 사항은 미결정 상태로 남는다.

### READY-02. 랜딩 페이지의 두 탐색 기능 차별화

- 상태: `DONE`
- 우선순위: 높음
- 목적: 연구 주제 허브와 자료 해설형 아카이브가 서로 다른 역할로 인식되게 한다.
- 기준 문서: `docs/proposal.md`, `docs/launch-readiness.md`
- 작업:
  - 기존 홈 컴포넌트와 데이터 흐름을 먼저 확인한다.
  - 연구 주제 허브는 생애·말씀·업적을 보여주는 주요 탐색 영역으로 유지한다.
  - 자료 아카이브는 같은 형태의 주제 카드 반복이 아니라 `처음 읽을 자료` 중심의 조밀한 목록 또는 읽기 경로로 표현한다.
  - 기존 데이터만 사용하고 공식 연구 내용을 임의로 만들지 않는다.
  - 새로운 UI·모션 의존성을 추가하지 않는다.
  - 모바일과 데스크톱에서 정보 위계와 내부 링크를 확인한다.
- 완료 조건:
  - 두 섹션의 제목을 가려도 레이아웃과 정보 구조에서 역할 차이가 보인다.
  - 홈에서 `주제 → 대표 자료 → 다음 자료` 흐름으로 이동할 수 있다.
  - 빈 자료 상태에서도 잘못된 추천이나 존재하지 않는 링크를 노출하지 않는다.
  - `npm run lint`와 `npm run build`가 통과한다.

### READY-03. 주제·자료 연결 무결성 점검

- 상태: `DONE`
- 우선순위: 높음
- 목적: 현재 slug 기반 수동 연결이 조용히 끊어진 상태를 찾고 수정한다.
- 작업:
  - `src/lib/topics.ts`, `src/lib/material-guides.ts`, `prisma/seed.ts`의 주제 slug, 카테고리 slug, 추천 자료 slug를 대조한다.
  - 공개 라우트와 내부 링크의 대상이 실제로 존재하는지 확인한다.
  - 불일치는 기존 구조 안에서 가장 작은 수정으로 해결한다.
  - 공식 콘텐츠를 새로 작성하거나 새 데이터 모델을 만들지 않는다.
- 완료 조건:
  - 생애·말씀·업적 주제의 카테고리 연결이 seed 데이터와 일치한다.
  - 추천 자료가 없을 때 기존 fallback이 정상 작동한다.
  - 확인한 연결 관계와 예외를 관련 운영 문서에 짧게 남긴다.
  - `npm run lint`와 `npm run build`가 통과한다.

### READY-04. 접근성 및 기본 인터페이스 점검

- 상태: `DONE`
- 우선순위: 중간
- 목적: 공식 개시에 필요한 기본 접근성과 조작 피드백을 확보한다.
- 적용 지침: `.agents/skills/apple-design/SKILL.md`
- 작업:
  - 공개 페이지와 관리자 폼의 제목 구조, landmark, label, 키보드 포커스, 링크·버튼 구분을 점검한다.
  - 모바일 터치 영역, 텍스트 대비, 오류·성공 상태 전달을 점검한다.
  - 기존 애니메이션이 있다면 `prefers-reduced-motion` 대응을 확인한다.
  - 명백한 접근성 결함은 기존 CSS와 HTML로 수정한다.
  - Apple 스타일을 이유로 장식 효과나 모션 라이브러리를 추가하지 않는다.
- 완료 조건:
  - 키보드만으로 주요 공개 탐색과 관리자 폼을 사용할 수 있다.
  - 입력 오류와 성공 상태가 색상만으로 전달되지 않는다.
  - 움직임이 필수 정보를 가리거나 reduced-motion 설정을 무시하지 않는다.
  - `npm run lint`와 `npm run build`가 통과한다.

### READY-05. 현재 관리자 운영 안내서 작성

- 상태: `DONE`
- 우선순위: 중간
- 목적: 단일 관리자가 현재 구현된 기능을 안전하게 운영할 수 있게 한다.
- 산출물: `docs/admin-operations.md`
- 작업:
  - 로그인, 게시글 초안·공개·보관, slug 관리, 문의 상태 변경 흐름을 실제 화면과 코드 기준으로 설명한다.
  - 게시글 및 카테고리 slug 변경 시 주제·추천 연결 확인 사항을 포함한다.
  - 환경 변수의 실제 값이나 운영 비밀은 기록하지 않는다.
  - 아직 없는 회원 승인, 파일 업로드, 복원 기능을 있는 것처럼 설명하지 않는다.
- 완료 조건:
  - 새 운영자가 현재 관리자 화면의 지원 범위와 제한을 이해할 수 있다.
  - 데이터 삭제 대신 보관 상태를 사용하는 현재 정책이 명시되어 있다.

### READY-06. 로컬 공식 개시 QA

- 상태: `DONE`
- 우선순위: 중간
- 목적: 배포 전 현재 저장소에서 확인 가능한 공개·관리자 흐름을 검증한다.
- 작업:
  - `npm run lint`와 `npm run build`를 실행한다.
  - 홈, 주제 목록·상세, 자료 목록·상세, 공지 목록·상세, 문의, 로그인, 관리자 경로를 데스크톱과 모바일 크기로 확인한다.
  - 인증이 필요한 변경 작업은 로컬 개발 DB에서만 수행하고, 기존 데이터가 중요하거나 환경이 불명확하면 읽기 검증까지만 한다.
  - 발견한 재현 가능한 결함은 현재 범위 안에서 수정하고 다시 검증한다.
  - 결과와 남은 외부 환경 검증 항목을 `docs/launch-readiness.md`에 날짜와 함께 기록한다.
- 완료 조건:
  - 주요 경로에서 깨진 화면, 잘못된 링크, 처리되지 않은 런타임 오류가 없다.
  - 로컬에서 확인할 수 없는 Production 항목은 완료 처리하지 않는다.

### READY-07. 회원가입과 일반 로그인

- 상태: `DONE`
- 우선순위: 높음
- 목적: 연구원이 이메일과 비밀번호로 가입하고, 관리자 승인 후 로그인할 수 있게 한다.
- 개인정보 기준: `docs/privacy-policy.md`
- 승인된 최소 범위:
  - 공개 회원가입 계정은 `RESEARCHER`, `PENDING` 상태로 생성한다.
  - 관리자가 계정을 승인하거나 비활성화할 수 있다.
  - 승인된 연구원만 로그인할 수 있다.
  - 기존 환경 변수 기반 단일 관리자 로그인은 유지한다.
  - 소셜 로그인, `EDITOR`, 연구 결과 작성 권한, 커뮤니티는 포함하지 않는다.
- 작업:
  - 관련 Next.js 및 Auth.js 가이드를 먼저 확인한다.
  - Prisma에 최소 사용자 모델과 역할·승인 상태를 추가하고 migration을 만든다.
  - 별도 OAuth `Account` 모델은 만들지 않는다.
  - 비밀번호는 평문으로 저장하지 않고 안전한 단방향 해시와 사용자별 salt를 사용한다.
  - `/signup`에서 이름, 이메일, 비밀번호를 서버에서 검증하고 중복 이메일을 차단한다.
  - 기존 `/login`에서 환경 변수 관리자와 승인된 DB 연구원 로그인을 모두 지원한다.
  - 세션에 사용자 ID와 역할을 포함하되 클라이언트 입력으로 권한을 결정하지 않는다.
  - `/admin/users`에서 가입 대기·승인·비활성 상태를 최소 기능으로 관리한다.
  - 회원이 직접 탈퇴할 수 있게 하고, 탈퇴 시 세션 종료와 계정 개인정보 삭제를 함께 처리한다.
  - 회원가입 화면에 `docs/privacy-policy.md`의 수집 항목·보유기간·동의 거부 안내와 필수 동의를 반영한다.
  - 가입·로그인 오류는 계정 존재 여부나 승인 상태를 불필요하게 노출하지 않는 문구로 처리한다.
  - 회원가입, 승인 전 로그인 거부, 승인 후 로그인, 비활성화 후 로그인 거부를 검증하는 최소 테스트를 남긴다.
- 완료 조건:
  - 새 계정의 기본 역할과 상태가 서버 및 DB에서 강제된다.
  - 비밀번호 원문이 DB와 로그에 남지 않는다.
  - 미승인·비활성 계정은 세션을 만들 수 없다.
  - 연구원 세션으로 관리자 화면과 관리자 Server Action에 접근할 수 없다.
  - 기존 관리자 로그인과 로그아웃이 계속 작동한다.
  - migration, 최소 인증 테스트, `npm run lint`, `npm run build`가 통과한다.
- Production 적용 제한:
  - 운영 DB migration과 Production 배포는 별도 승인을 받은 뒤 수행한다.
  - 이메일 인증·비밀번호 재설정 메일은 발송 서비스가 결정되기 전까지 구현하지 않는다. 이 제한을 회원가입 화면과 운영 문서에 명시한다.

## 의사결정 또는 승인이 필요한 일

### WAITING-01. 공식 콘텐츠 반영

- 상태: `WAITING`
- 필요한 입력:
  - 생애·말씀·업적 공식 소개 원문
  - 각 주제의 핵심 질문
  - 대표 입문 자료와 공식 본문 또는 출처
  - 자료별 해설 요약과 읽기 포인트의 승인된 문안
- 승인 후 작업:
  - `src/lib/topics.ts`, 게시글 데이터, `src/lib/material-guides.ts`에 승인된 콘텐츠를 반영한다.

### WAITING-02. 개인정보 처리방침 공개 정보 확정

- 상태: `WAITING`
- 확정된 기준:
  - `docs/privacy-policy.md` 초안
  - 승인 회원정보는 탈퇴 시까지, 미승인 가입정보는 30일 보존
  - 문의 개인정보는 처리 완료 후 1년 보존
  - 접속·인증 보안기록은 3개월 보존
  - 탈퇴 시 즉시 이용 중지 후 계정 개인정보 삭제
- 필요한 입력 및 확인:
  - 개인정보 보호 담당부서, 담당자 또는 책임자
  - 개인정보 담당 이메일과 전화번호
  - Vercel·Supabase의 처리 지역, 로그·백업 보유기간과 국외이전 고지
  - 처리방침 공고일과 시행일
- 승인 후 작업:
  - 처리방침 페이지와 회원가입·문의 동의를 구현하고 footer에서 연결한다.

### WAITING-03. Vercel·Supabase 운영 설정 확정

- 상태: `WAITING`
- 확정된 사항:
  - 배포 환경은 Vercel
  - 운영 PostgreSQL은 Supabase
  - `main`은 Production, 다른 브랜치는 Preview 배포로 사용 중
- 필요한 확인 및 결정:
  - 공식 도메인
  - Vercel Production Branch가 실제로 `main`인지 여부
  - Preview와 Production DB 분리 여부
  - Supabase 요금제와 자동 백업 보존 범위
- 필요한 승인:
  - Production 환경 변수 변경
  - 운영 DB Migration 적용
  - DNS 변경과 Production 배포
- 승인 후 작업:
  - `docs/deployment-checklist.md`를 기준으로 Vercel·Supabase 설정과 Production smoke test를 완료한다.

### WAITING-04. 백업·복구·모니터링 운영 정책

- 상태: `WAITING`
- 필요한 결정:
  - 백업 주기와 보존 기간
  - 장애 알림 수신자와 채널
  - 장애 대응 담당자
  - 배포 실패 시 rollback 기준
- 필요한 승인:
  - 외부 모니터링 또는 알림 서비스 연결
  - 운영 DB 복원 시험

### WAITING-05. 소셜 로그인
