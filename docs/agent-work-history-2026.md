### READY-07. 회원가입과 일반 로그인

- 상태: `DONE`
- 우선순위: 높음
- 목적: 연구원이 이메일과 비밀번호로 가입하고, 관리자 승인 후 로그인할 수 있게 한다.
- 개인정보 기준: `docs/privacy-policy.md`
- 승인된 최소 범위:
  - 공개 회원가입 계정은 `RESEARCHER`, `PENDING` 상태로 생성한다.
  - 관리자가 계정을 승인하거나 비활성화할 수 있다.
  - 승인된 연구원만 로그인할 수 있다.
  - 기존 환경 변수 기반 단일 관리자 로그인은 유지한다.
  - 소셜 로그인, `EDITOR`, 연구 결과 작성 권한, 커뮤니티는 포함하지 않는다.
- 작업:
  - 관련 Next.js 및 Auth.js 가이드를 먼저 확인한다.
  - Prisma에 최소 사용자 모델과 역할·승인 상태를 추가하고 migration을 만든다.
  - 별도 OAuth `Account` 모델은 만들지 않는다.
  - 비밀번호는 평문으로 저장하지 않고 안전한 단방향 해시와 사용자별 salt를 사용한다.
  - `/signup`에서 이름, 이메일, 비밀번호를 서버에서 검증하고 중복 이메일을 차단한다.
  - 기존 `/login`에서 환경 변수 관리자와 승인된 DB 연구원 로그인을 모두 지원한다.
  - 세션에 사용자 ID와 역할을 포함하되 클라이언트 입력으로 권한을 결정하지 않는다.
  - `/admin/users`에서 가입 대기·승인·비활성 상태를 최소 기능으로 관리한다.
  - 회원이 직접 탈퇴할 수 있게 하고, 탈퇴 시 세션 종료와 계정 개인정보 삭제를 함께 처리한다.
  - 회원가입 화면에 `docs/privacy-policy.md`의 수집 항목·보유기간·동의 거부 안내와 필수 동의를 반영한다.
  - 가입·로그인 오류는 계정 존재 여부나 승인 상태를 불필요하게 노출하지 않는 문구로 처리한다.
  - 회원가입, 승인 전 로그인 거부, 승인 후 로그인, 비활성화 후 로그인 거부를 검증하는 최소 테스트를 남긴다.
- 완료 조건:
  - 새 계정의 기본 역할과 상태가 서버 및 DB에서 강제된다.
  - 비밀번호 원문이 DB와 로그에 남지 않는다.
  - 미승인·비활성 계정은 세션을 만들 수 없다.
  - 연구원 세션으로 관리자 화면과 관리자 Server Action에 접근할 수 없다.
  - 기존 관리자 로그인과 로그아웃이 계속 작동한다.
  - migration, 최소 인증 테스트, `npm run lint`, `npm run build`가 통과한다.
- Production 적용 제한:
  - 운영 DB migration과 Production 배포는 별도 승인을 받은 뒤 수행한다.
  - 이메일 인증·비밀번호 재설정 메일은 발송 서비스가 결정되기 전까지 구현하지 않는다. 이 제한을 회원가입 화면과 운영 문서에 명시한다.
- 완료 기록 (2026-07-20): 연구자 `User` 모델과 migration, scrypt 비밀번호 해시, 가입·승인 상태별 로그인, 역할 세션, 회원 관리, 탈퇴를 구현함. 관리자 데이터 조회와 Server Action에 `ADMIN` 역할 검사를 적용하고 관리자 로그인·로그아웃 및 비로그인 보호 경로를 로컬 확인함. Prisma schema 검증·client 생성, 인증 테스트 3개, lint/build 통과.
- 남은 조건: `20260720000000_add_researcher_users`의 Production 적용·배포는 별도 승인 필요. 이메일 인증·비밀번호 재설정과 소셜 로그인은 미구현 상태 유지

### READY-08. 회원가입 오류 상태와 신청 완료 안내 개선

- 상태: `DONE`
- 우선순위: 높음
- 목적: 회원가입 실패와 성공 시 사용자가 현재 상태와 다음 행동을 분명히 알 수 있게 한다.
- 작업:
  - 비밀번호와 비밀번호 확인이 일치하지 않을 때 이름·이메일·개인정보 동의 상태를 유지한다.
  - 오류가 난 경우 비밀번호 관련 필드만 비우고, 해당 오류 메시지와 입력 위치를 접근성 있게 연결한다.

#### 승인 후 병목 개선 순서

1. **측정부터 추가한다.** `auth.ts`와 `login-throttle.ts`에서 제한 처리(풀/트랜잭션 및 내부 단계), Supabase 인증, 회원 조회·최초 갱신, 성공 후 제한 삭제, 전체 authorize 시간을 나눠 측정한다. 브라우저에서는 제출→pending 표시, 액션 응답, `/auth/continue`, 최종 화면 표시를 분리한다. 임의 요청 ID·구간명·소요 시간만 기록하고 이메일·IP·비밀번호·토큰·쿠키·전체 요청/응답은 남기지 않는다. 테스트 계정·운영 계측 승인을 받은 뒤 관리자/연구자, 성공/실패/차단, 첫 요청/재요청을 비교한다. 소수 표본은 중앙값·최댓값·표본 수로 보고하고 충분한 표본 없이 p95를 확정하지 않는다.
2. **DB 왕복이 지배적이면 제한 처리부터 줄인다.** 매 로그인에서 수행하는 전체 만료 레코드 정리를 인증 필수 경로 밖으로 옮길 수 있는 기존 유지보수 수단을 확인하고, 24시간 보존 정책을 지킬 방법이 정해진 뒤 변경한다. 키별 초기화·확인·증가를 원자적인 조건부 upsert 등으로 합치는 최소 변경을 검토한다. 적용 전 동시 요청과 잠금 경계를 테스트한다. 단순 `Promise.all`이나 프로세스 메모리 제한기로 교체하지 않는다. 계정 5회/IP 20회, 15분 창·차단, 관리자 fail-closed 및 기존 오류 정책을 임의로 완화하지 않는다. 성공 후 제한 삭제도 측정 없이 fire-and-forget으로 옮기지 않는다.
3. **외부 호출이 지배적이면 연결 환경을 확인한다.** 실제 Vercel 함수 실행 지역과 Supabase Auth·DB 지역, 커넥션 풀 대기, 첫 요청 초기화 비용을 확인한다. 지역/풀 설정 변경은 근거와 별도 운영 승인 후 적용한다. 비밀번호 검증을 생략하거나 Supabase와 병렬로 무조건 회원 정보를 조회하지 않는다. SDK 교체·Redis·새 인증 제공자 도입은 범위 밖이다.
4. **후속 이동이 지배적일 때만 단축한다.** 검증된 서버 세션 역할에 따라 안전하게 직접 목적지를 정할 수 있는지 설치된 Auth.js 동작을 확인한다. 클라이언트 username만으로 관리자 목적지나 권한을 판단하지 않는다. 중간 경로 제거가 복잡하거나 절감이 작으면 유지한다. 홈 캐시 미스가 원인이면 무거운 자료 영역만 Suspense로 분리하는 방안을 검토하고, 인증 화면 전체 재구성은 하지 않는다.
5. **동일 조건으로 전후 검증한다.** 단계별 시간·실제 SQL 왕복 수와 클릭→최종 화면 시간을 비교해 효과를 기록한다. 승인/미승인/비활성/이메일 미확인/세션 무효화 검사를 보존한다. 운영 지연이 확인되지 않은 단계는 변경하지 않는다.

#### 구현 원칙과 승인 후 순서

1. **커서 원인부터 공통 수정:** native button과 Button을 함께 덮는 최소 규칙을 선택한다. 활성 버튼만 pointer로 표시하고 disabled는 default 또는 not-allowed 중 일관된 정책으로 분리한다. a[href]의 기본 동작은 보존하고 텍스트 입력은 text 커서를 유지한다. select·checkbox·label·summary·파일 선택은 실제 클릭 부위별로 검증하며 모든 요소에 pointer를 강제하지 않는다.
2. **누름과 처리 중 상태 분리:** 커서는 클릭 가능성, active는 클릭 수신, pending은 서버 처리 상태다. 공통 버튼은 색상 중심으로 보완하고 미세 scale이 필요하면 포인터 입력·motion-safe에 한정한다. 입력·키보드 동작을 애니메이션 때문에 늦추지 않는다. disabled:hover/active가 활성처럼 보이지 않게 한다.
3. **서버 폼만 필요한 pending 추가:** 설치된 Next.js forms 가이드를 구현 전에 읽고 기존 LoginSubmit의 폼 하위 useFormStatus 패턴을 재사용한다. 공통화는 실제 중복 제출 버튼 범위까지만 한다. 폼 전체를 클라이언트로 바꾸지 않고, 여러 제출 의도·formNoValidate·hidden 입력·서버 권한 및 검증을 보존한다. 기존 useActionState/busy 폼은 유지한다.
4. **링크는 탐색 의미 유지:** 링크 자체의 hover/focus/active와 클릭 영역을 점검한다. 실제 느린 탐색이 확인될 때만 해당 경로의 이동 중 표시를 검토한다. 전역 로딩 상태 관리자·새 UI 라이브러리·모든 링크의 spinner는 추가하지 않는다. Emil의 상태별 즉시 피드백과 Ponytail의 기존 공통 요소 재사용 원칙을 적용한다.
5. **완료 검증:** 공개/회원/관리자에서 활성·disabled·pending의 computed cursor, hover/active/focus, 모바일 메뉴, Hero/연대기, 키보드 Enter/Space, reduced-motion을 확인한다. 로컬 격리/모의 응답으로 지연·실패·이중 클릭·상태 변경 경합·submit intent 보존을 검사하고 실패 후 재시도·성공 후 상태 반영을 확인한다. 실제 회원 승인/탈퇴/메일/게시글 변경은 별도 승인 없이 실행하지 않는다. 코드 구현 시 lint/build 및 최소 회귀 검사를 수행한다.

- 문제·대상: `src/app/admin/posts/actions.ts`, 관리자 목록·수정 화면, `src/lib/admin-posts.ts`, 공개 조회·캐시 호출부와 관련 테스트·운영 안내. 현재 보관은 `ARCHIVED` 상태 전환뿐이며 별도 삭제 화면·액션이 없다.
- 최소 구현: 보관된 공지·홍보 글에만 삭제 확인과 실행 UI를 제공한다. 서버에서 유효한 관리자·글 유형·보관·미삭제 조건을 최종 쓰기 시 재검사하고 기존 `deletedAt`으로 논리 삭제한다. 관리자 목록의 건수·행 조회, 직접 수정 주소, 수정·공개·보관 액션에서 삭제 글을 제외하고 관련 공개 캐시를 갱신한다. 삭제와 재공개가 경합해도 삭제 글을 되살리지 않게 조건부 갱신을 적용한다. 실패는 성공으로 표시하지 않고 재시도 가능한 안내를 제공한다.
- 정합성·완료 기준: 게시글과 연결 첨부가 있다면 삭제 표식을 트랜잭션으로 함께 기록하고 기존 정책대로 Storage 원본 정리를 요청한다. Storage 실패 시 숨김 상태·첨부 경로·실패 기록을 보존하고 원본 정리 완료 전에는 삭제 완료로 표시하지 않는다. 권한 없는 요청·활성 글·연구 글 거부, 보관 공지/홍보 삭제, 중복 요청, 삭제 후 목록·직접 조회·수정 차단, DB 실패 롤백과 재공개 경합을 관련 테스트로 검증한다. 첨부가 있는 경우 원본 정리 실패·재시도도 검증하며 실제 DB 경합은 격리 DB에서만 확인한다.
- 범위 제한: DB 행·콘텐츠 영구 삭제, 휴지통·복원 화면, 연구 글 삭제 기능, 새 업로드 기능·자동 정리 작업은 추가하지 않는다. 운영 안내의 지원 범위는 공지·홍보 삭제만 갱신한다. `READY-34` 완료를 필수로 삼지 말고 삭제 자체의 최소 오류 안내를 포함한다. 관련 테스트와 필수 lint·build를 수행하며 운영 데이터 삭제·Production 배포는 제외한다.

- 완료 기록 (2026-10-29): 보관된 공지·홍보 글의 확인 후 논리 삭제와 첨부 원본 정리를 구현했다. 글·첨부 표식을 트랜잭션으로 남기고, 정리 실패 시 경로·오류 로그를 보존하며 같은 화면에서 재시도한다. 관리자 목록·직접 수정·수정/보관 액션에서 삭제 글을 제외하고 최종 갱신 조건으로 재공개 경합을 막았다. 격리 PostgreSQL 17.11과 Storage 대역으로 권한·상태·중복·롤백·실패/재시도·동시 갱신을 검증했다. 브라우저에서 확인 취소·삭제·직접 수정 차단·정리 실패 후 재시도를 확인했다. 관련 테스트 8건, lint, production build 통과.
- 검증 한계: 실제 Supabase Storage와 Production은 변경하거나 검증하지 않았다. 정리 실패 후 화면을 떠나면 삭제 글이 목록에 없어 서버 로그와 승인된 유지보수 절차로 재처리한다.

### READY-36. 공지·홍보 생성 카테고리 허용 범위 제한

- 상태·우선순위: `DONE`, P2 — 2026-10-29 구현과 검증 완료.
- 문제·대상: `src/app/admin/posts/new/page.tsx`, `createPost`가 있는 `src/app/admin/posts/actions.ts`, `src/lib/admin-posts.ts`와 관련 테스트. 활성 연구 카테고리가 있으면 생성 화면에서 홍보자료로 표시되고 작성자 없는 연구 글 생성까지 허용된다. 현재 seed에 연구 카테고리가 없더라도 서버 입력 경계에서 거부해야 한다.
- 최소 구현: 새 글 카테고리 목록에 기존 `getAdminEditableCategoriesWhere`, 생성 액션에 `getAdminEditableCategoryWhere`를 재사용해 활성 `NOTICE`·`PROMOTION`만 허용한다. 허용 카테고리가 없으면 저장을 막고 기존 안내를 유지한다. 최종 글 유형은 검증된 카테고리에서만 결정한다.
- 완료 기준·검증: 연구·비활성·없는 카테고리를 조작 제출해도 게시글이 생성되지 않는지 액션 수준에서 검증한다. 활성 공지·홍보 카테고리의 임시저장·공개 성공 및 올바른 유형 저장, 생성 화면의 연구 카테고리 제외와 허용 목록이 빈 경우를 확인한다. helper 결과만 비교하는 테스트로 완료를 대신하지 않는다.
- 범위 제한: 카테고리 관리 UI·데이터 모델·운영 카테고리 데이터는 변경하지 않는다. WAITING-17/D2의 연구 글 수정 차단은 재구현하지 않고 생성 경계만 보완한다. `READY-34`의 오류 표현 개선과 독립적으로 진행하며 관련 테스트와 필수 lint·build만 실행한다.

- 완료 기록 (2026-10-29): 생성 화면과 서버 액션에 기존 관리자 카테고리 조건을 적용해 활성 공지·홍보만 허용했다. 액션 테스트에서 연구·비활성·없는 카테고리 거부와 공지·홍보의 임시저장·공개 유형을 확인했고, 화면 렌더링 테스트에서 연구 카테고리 제외와 허용 목록이 비었을 때 저장 차단을 확인했다. 관련 테스트 5건, lint, production build 통과. 모의 DB를 사용했으며 실제 DB·브라우저와 Production은 변경하거나 검증하지 않았다.
