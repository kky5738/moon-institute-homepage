# 문선명 연구소 홈페이지 공식 개시 준비 점검

## 문서 목적

이 문서는 홈페이지를 공식적으로 개시하기 전에 제품, 콘텐츠, 회원·권한, 운영, 배포, 보안 준비 상태를 점검하고 결정 사항을 기록하기 위한 문서다.

세부 기능 방향은 `docs/proposal.md`, 배포 절차는 `docs/deployment-checklist.md`, 데이터 구조는 `docs/data-model.md`, AWS 인프라 계획은 `docs/aws-plan.md`에서 관리한다.

## 종합 판단

현재 프로젝트는 **공개 홈페이지와 단일 관리자 운영** 형태로는 공식 개시에 가까운 상태다. 공지사항, 홍보자료, 문의 접수와 관리자 게시글·문의 관리 기능이 구현되어 있으며, 2026년 7월 12일 기준 `npm run lint`와 `npm run build`가 통과했다.

반면 **연구원이 가입하고 직접 연구 결과를 게시하는 협업 플랫폼**으로 운영하기 위한 회원, 승인, 역할, 작성자, 게시 검수 구조는 아직 없다.

공식 개시는 다음 두 단계로 나누는 것을 권장한다.

1. 단일 관리자 체제의 공개 홈페이지 개시
2. 연구원 회원·권한·연구 결과 게시 기능 도입

## 1. 연구 주제 허브와 자료 해설형 아카이브

### 현재 판단

두 기능이 비슷하게 보이는 가장 큰 이유는 실제 연구 콘텐츠가 부족하기 때문이다. 현재 문구는 연구 내용을 보여주기보다 앞으로 제공할 기능을 안내하는 성격이 강하다.

화면 구성도 두 기능의 차이를 약하게 만든다. 둘 다 비슷한 카드와 링크 중심으로 표현하면 실제 콘텐츠가 추가되어도 구분이 흐릴 수 있다.

### 역할 구분

| 기능 | 핵심 질문 | 주요 콘텐츠 | 적합한 화면 표현 |
| --- | --- | --- | --- |
| 연구 주제 허브 | 무엇을 연구하는가? | 연구 범위, 핵심 질문, 세부 주제, 대표 자료 | 큰 주제 중심의 탐색 영역 |
| 자료 해설형 아카이브 | 무엇부터 어떻게 읽는가? | 자료 유형, 난이도, 읽기 순서, 출처, 다음 자료 | 조밀한 목록과 읽기 경로 |

### 권장 방향

- 랜딩 페이지에서 두 기능을 동일한 카드 그리드로 반복하지 않는다.
- 연구 주제 허브는 생애·말씀·업적을 보여주는 주요 탐색 영역으로 둔다.
- 자료 아카이브는 `처음 읽을 자료`, `최근 추가된 자료`처럼 자료 중심의 목록으로 표현한다.
- 자료가 충분하지 않은 동안에는 전체 아카이브보다 대표 입문 자료 세 건을 우선 노출한다.
- 구체적인 기능 및 콘텐츠 기준은 `docs/proposal.md`를 따른다.

### 개시 전 최소 콘텐츠

- [ ] 생애·말씀·업적의 공식 소개문이 각각 준비되어 있다.
- [ ] 각 주제에 핵심 질문이 3개 이상 있다.
- [ ] 각 주제에 대표 입문 자료가 1개 이상 있다.
- [ ] 대표 자료에 실제 본문 또는 공식 원문이 있다.
- [ ] 대표 자료에 해설 요약과 읽기 포인트가 있다.
- [ ] 주제에서 자료, 자료에서 다음 자료로 이동할 수 있다.

## 2. Apple 스타일 인터페이스

### 우선순위

Apple 스타일 적용은 공식 콘텐츠, 운영 체계, 회원·권한, 배포 준비보다 우선순위가 낮다.

### 적용 원칙

이 프로젝트에서 Apple 스타일은 화려한 유리 효과나 많은 애니메이션보다 다음 원칙을 중심으로 적용한다.

- 현재 위치와 다음 이동 경로가 명확한 탐색
- 입력과 클릭에 즉시 반응하는 피드백
- 절제되고 일관된 움직임
- 읽기 좋은 한글 타이포그래피와 간격
- 모바일에서 충분한 터치 영역
- `prefers-reduced-motion` 등 접근성 대응
- 중요한 콘텐츠가 먼저 보이는 정보 위계

회원·편집 화면이 구현되면 저장 상태, 오류 안내, 제출 완료, 작성 중 이탈 경고 등 운영 인터페이스에 우선 적용한다. 랜딩 페이지 효과만을 위해 새로운 모션 의존성을 추가하지 않는다.

## 3. 회원가입과 소셜 로그인

### 현재 상태

현재 인증은 환경 변수에 저장한 단일 관리자 계정만 지원한다. DB에는 사용자, 소셜 계정, 역할, 승인 상태, 게시글 작성자 관계가 없다.

소셜 로그인은 사용자의 신원을 확인하는 수단이며, 홈페이지 관리 권한을 자동으로 부여하는 수단이 아니다.

### 권장 가입 흐름

연구원 전용 운영을 전제로 다음 흐름을 권장한다.

1. 사용자가 지원하는 소셜 계정으로 로그인한다.
2. 최초 계정은 `PENDING` 상태로 생성한다.
3. 관리자가 실제 연구원 여부를 확인하고 승인한다.
4. 승인된 연구원만 작성 화면에 접근한다.
5. 연구원은 연구 결과를 초안으로 작성한다.
6. 관리자 또는 편집자가 검토한 뒤 공개한다.

### 최소 역할

- `ADMIN`: 회원 승인, 모든 콘텐츠 관리 및 공개
- `RESEARCHER`: 본인 초안 작성 및 수정
- `EDITOR`: 실제 검수 업무가 분리될 때만 추가

현재 게시글의 `DRAFT`, `PUBLISHED`, `ARCHIVED` 상태는 게시 검수 흐름에 재사용한다.

### 결정이 필요한 질문

- [ ] 누구나 가입할 수 있는가, 초대 또는 관리자 승인이 필요한가?
- [ ] Google, Kakao, Naver 중 어떤 로그인 제공자를 지원할 것인가?
- [ ] 연구원이 직접 공개할 수 있는가, 관리자 검수가 필요한가?
- [ ] 연구원은 본인 글만 수정할 수 있는가?
- [ ] 탈퇴하거나 권한을 잃은 연구원의 게시글은 누구에게 귀속되는가?
- [ ] 연구 결과는 텍스트 게시글만 포함하는가, PDF와 첨부파일도 포함하는가?
- [ ] 수정 이력과 게시 승인 기록을 보존해야 하는가?
- [ ] 커뮤니티는 연구원 전용인가, 별도 승인 회원도 포함하는가?

### 단계적 구현 범위

첫 단계에서는 연구원 계정, 관리자 승인, 본인 초안 작성까지만 구현한다. 역할별 접근 제어가 안정된 뒤 게시 검수와 편집자 역할을 추가한다. 커뮤니티는 실제 운영 수요가 확인된 뒤 별도 범위로 다룬다.

## 4. 보안 준비

보안은 별도 작업으로 상세 점검하되, 회원·권한 모델은 회원 기능 구현 전에 확정해야 한다. 권한 구조 자체가 보안 설계의 기반이기 때문이다.

### 공식 개시 전 최소 점검

- [ ] 운영 관리자 비밀번호와 `AUTH_SECRET`을 안전하게 생성하고 보관한다.
- [ ] 로그인과 공개 문의 폼의 요청 제한 및 자동화된 악용 방지 방식을 정한다.
- [ ] 모든 관리자 Server Action이 서버에서 권한을 확인한다.
- [ ] 운영 로그에 비밀번호, 인증 토큰, 불필요한 개인정보가 남지 않는다.
- [ ] 운영 DB 백업과 복원 절차를 마련하고 실제 복원을 시험한다.
- [ ] 개인정보 처리방침을 공개한다.
- [ ] 문의 데이터의 보존 기간과 삭제 요청 처리 기준을 정한다.
- [ ] 운영 의존성과 배포 환경에 대한 보안 점검을 수행한다.

현재 홈페이지는 문의 기록의 장기 보존을 안내하므로, 실제 보존 기간과 정보 주체의 삭제 요청 처리 원칙을 공식 개시 전에 확정해야 한다.

## 5. 공식 운영 준비도

### 현재 확인된 준비 상태

- [x] 공개 랜딩 페이지가 있다.
- [x] 연구 주제 목록과 상세 경로가 있다.
- [x] 자료 목록과 상세 경로가 있다.
- [x] 공지사항 목록과 상세 경로가 있다.
- [x] 문의·참여 신청 접수가 가능하다.
- [x] 단일 관리자 로그인과 보호된 관리자 경로가 있다.
- [x] 게시글 작성·수정·보관 처리가 가능하다.
- [x] 문의 상태 관리가 가능하다.
- [x] `npm run lint`가 통과한다.
- [x] `npm run build`가 통과한다.

### 개시 전 우선순위 높음

- [ ] 연구소 공식 소개문과 실제 연구 콘텐츠를 확정한다.
- [ ] 운영 도메인과 대표 연락처를 확정한다.
- [ ] 개인정보 처리방침을 작성하고 연결한다.
- [ ] 운영 DB를 준비하고 마이그레이션을 적용한다.
- [ ] 자동 백업과 복원 절차를 마련한다.
- [ ] 장애 확인 방법과 운영 담당자의 대응 절차를 문서화한다.
- [ ] 실제 배포 환경에서 전체 smoke test를 수행한다.
- [ ] Vercel과 AWS 중 첫 공식 배포 환경을 결정한다.

### 개시 전 우선순위 중간

- [ ] 검색엔진용 sitemap과 robots 설정을 준비한다.
- [ ] 공유용 메타데이터와 대표 이미지를 준비한다.
- [ ] 주요 공개 페이지의 접근성을 점검한다.
- [ ] 콘텐츠 작성, 검수, 공개 절차를 정한다.
- [ ] 연구 자료의 출처 표기와 수정 기준을 정한다.
- [ ] 관리자 작업 안내서를 작성한다.

## 6. 배포 및 운영 결정

현재 `docs/deployment-checklist.md`는 Vercel 배포를 기준으로 작성되어 있지만 프로젝트 목표에는 AWS 배포가 명시되어 있다.

### 결정이 필요한 질문

- [ ] 첫 공식 배포는 Vercel인가, AWS인가?
- [ ] 운영 DB 제공자는 어디인가?
- [ ] Preview와 Production DB를 분리할 것인가?
- [ ] 장애와 오류 알림을 누가 어떤 채널로 받는가?
- [ ] 정기 백업 주기와 보존 기간은 얼마인가?
- [ ] 배포 실패 시 이전 버전으로 되돌리는 절차는 무엇인가?
- [ ] 운영 중 콘텐츠와 회원 문의를 담당할 사람은 누구인가?

배포 환경이 결정되면 Vercel을 선택한 경우 `docs/deployment-checklist.md`를 확정하고, AWS를 선택한 경우 비어 있는 `docs/aws-plan.md`에 인프라와 배포 절차를 작성한다.

## 7. 공식 개시 보류 조건

다음 중 하나라도 충족되지 않으면 공개 홈페이지의 공식 개시를 보류한다.

- 공식 소개문과 최소 대표 콘텐츠가 없다.
- 개인정보 처리방침과 문의 데이터 처리 기준이 없다.
- 운영 DB의 백업 및 복구 방법이 없다.
- 관리자 계정과 비밀값이 개발용 상태로 남아 있다.
- 실제 배포 환경에서 게시글 작성과 문의 접수 흐름을 검증하지 않았다.
- 장애 발생 시 확인하고 대응할 담당자와 절차가 없다.

회원 기능은 다음 조건이 충족될 때까지 공개하지 않는다.

- 가입 및 승인 정책이 결정되지 않았다.
- 역할별 권한표가 없다.
- 서버에서 소유권과 역할을 검증하지 않는다.
- 계정 정지·탈퇴와 기존 게시물 귀속 정책이 없다.

## 8. 권장 진행 순서

1. 공식 개시 범위를 단일 관리자 공개 홈페이지로 확정한다.
2. 공식 콘텐츠와 개인정보 처리방침을 준비한다.
3. 첫 배포 환경과 운영 DB를 결정한다.
4. 백업, 복구, 모니터링, smoke test 절차를 마련한다.
5. 공개 홈페이지를 개시한다.
6. 회원·승인·역할·게시 검수 정책을 확정한다.
7. 연구원 계정과 초안 작성 기능을 구현한다.
8. 실제 필요가 확인되면 편집자 역할과 커뮤니티를 확장한다.
